SARTHI
AI-Powered Heritage Companion
Product Requirements Document (PRD)
Tagline: “From where you are, to what it means.”
Build target: Real working mobile application prototype

Document Control
1. Product Definition
SARTHI is an AI-powered, mobile-first, offline-capable heritage companion focused on helping visitors understand Indian heritage sites in context. The product is not positioned as a booking app.
Core product principle: Sarthi should not simply answer “What is this monument?” It should answer: “What am I looking at RIGHT NOW, why does it matter, what should I explore next, and can you explain it in a language and format I understand?”
2. Problem Statement
Fragmented information while visiting heritage sites.
Unreliable or outdated information.
Weak historical and cultural context.
Lack of personalization.
Language and accessibility barriers.
Poor connectivity.
Lack of structure-level guidance.
Difficulty discovering lesser-known heritage places.
3. Product Solution
Verified heritage knowledge with provenance.
AI explanations through an API-ready service abstraction.
Location-aware guidance using GPS and a geofencing-ready architecture.
Personalized micro-itineraries.
Multilingual text and audio.
Offline site packs.
Navigation and site maps.
Real-time information abstractions.
Local experiences.
4. Product Goals
Deliver a functional, real mobile application rather than a static UI mockup.
Make heritage knowledge understandable, contextual, and provenance-aware.
Support exploration even when connectivity is unavailable for downloaded content.
Personalize discovery and itinerary generation using stored user preferences.
Support multilingual UI with English, Hindi, and Marathi fully implemented in the prototype.
Provide accessibility controls and site accessibility information.
Keep external services replaceable through service abstractions.
Provide a reliable hackathon/demo flow without making demo mode look fake or game-like.
5. Non-Goals / Explicit Scope Exclusions
AR functionality is NOT implemented in this version.
Real payments are NOT implemented.
A full admin application is NOT implemented.
Live map APIs are NOT required initially; mock map data is acceptable behind an API-ready architecture.
Real external AI/LLM integration is not required for the prototype; structured heritage data may back the mock intelligent response engine.
API secrets must never be exposed in the React Native client.
6. Target Product Experience
7. Users & Primary Use Cases
Tourist visiting an Indian heritage site and wanting contextual explanations.
Visitor with limited time who needs a personalized 30–45 minute or longer route.
Visitor who prefers Hindi, Marathi, or another supported language.
Visitor who needs accessible routes/facilities information.
Visitor with poor connectivity who needs downloaded site content.
Demo/judge who needs to experience the core location-aware, AI, itinerary, and offline flow without physically moving.
8. Information Architecture & Navigation
Primary bottom navigation: HOME, EXPLORE, PLAN, GUIDE, PROFILE.
9. Onboarding Requirements
The onboarding flow contains 3–4 value-oriented screens followed by preference collection.
Interest categories: Architecture, History, Culture, Religion, Photography, Local Stories, Food, Craft, Nature.
Allow Skip where appropriate.
Persist onboarding preferences locally.
10. Home Requirements
Header: “Namaste, [Name] 👋”
Subtitle: “Where would you like to explore today?”
Search: “Search heritage sites, cities or experiences”
Hero: “Explore India's Stories” with featured heritage destination.
Quick actions: Explore Nearby, Plan My Visit, Download Site, AI Guide.
Recommended for you section based on user interests.
Popular Heritage Sites section.
Continue Exploring section for recently viewed sites.
Popular/recommended site cards should expose image, name, city/state, heritage category, UNESCO/ASI status where applicable, estimated visit duration, and offline availability.
11. Explore Requirements
Search-based discovery interface.
Filters: State, Distance, Heritage type, UNESCO, ASI, Duration, Accessibility, Offline available.
Categories: Fort, Temple, Palace, Monument, Cave, Museum, Archaeological Site, Cultural Landscape.
Each result: image, name, location, short description, distance, opening status, estimated visit time, offline pack status.
LIST / MAP toggle.
Map can use mock data initially; architecture must remain API-ready.
12. Heritage Site Detail Requirements
Reference example: Qutub Minar, Delhi, UNESCO World Heritage Site.
Header image.
Site name, city/state/location context.
UNESCO/ASI and other applicable badges.
Verified Knowledge, Offline Available, and Audio Available indicators where true.
Primary CTA: START EXPLORING.
Secondary CTA: DOWNLOAD SITE.
Sections: Overview, Why It Matters, Historical Timeline, Architecture, What You Are Looking At, Stories, Map, Facilities, Accessibility, Audio Guide, Nearby Experiences.
13. Verified Knowledge & Provenance Requirements
Important heritage facts must expose provenance. AI-generated claims must not be presented as unquestionable facts.
Displayed provenance metadata should include source, verification status, verifier where available, and last-updated date. Example source in the specification: Archaeological Survey of India.
14. Heritage Stories & Audio
Story cards covering Architecture, Historical Context, Hidden Detail, Local Story, and Why It Matters.
Actions: READ STORY and LISTEN.
Audio player: Play/Pause, Progress, Speed, Language.
Prototype may use bundled/mock audio files or placeholder audio service functions.
Audio service must be replaceable with a real TTS/audio service later.
15. AI Guide Requirements
AI Guide screen title: “Sarthi Guide”. Subtitle: “Ask me anything about this place.”
Suggested questions: “What am I looking at?”, “Why is this monument important?”, “Tell me the story in simple Hindi.”, “What should I see next?”, “I have 30 minutes. What should I explore?”, “Which parts are original?”
Chat supports user messages, AI responses, source citations, related places, and suggested follow-up questions.
AI behavior must be implemented behind aiService.ts rather than embedded directly in UI components.
Required abstraction methods: generateAnswer(), generateItinerary(), explainHeritage(), recommendNextStop().
Prototype response engine is backed by structured heritage data.
Future architecture may connect an LLM + RAG backend.
Never place an API secret in the mobile client.
16. Personalized Trip Planner
Title: “Plan My Heritage Experience”.
Inputs: Destination, Available time, Budget, Interests, Travel group, Age group, Mobility requirements, Preferred language.
Duration options: 30–45 min, 1–2 hours, 2–3 hours, Half day, Full day.
Generated itinerary includes time, stop, duration, total duration, walking distance, estimated cost, accessibility, and offline availability.
Actions: START ROUTE, SAVE PLAN, DOWNLOAD OFFLINE.
Reference itinerary sequence in the source: Main Gateway → Central Monument → Architectural Gallery → Hidden Heritage Point → Local Craft Experience. This is an illustrative product-flow example, not a factual claim about any particular site.
17. Location-Aware Experience
AR is excluded.
Use Expo Location for GPS.
Architecture must be geofencing-ready.
Support map selection, manual location selection, and QR-ready architecture.
When near a point, show contextual prompt such as “You're near the Main Gateway.”
Offer Architecture, History, Story, and Audio choices.
Development/demo mode must include SIMULATE LOCATION.
18. Map & Navigation
Site map screen with Entrance, Important structures, Toilets, Drinking water, Exit, Parking, Accessible route, Viewpoints, Food, Information desk.
Initial implementation may use mock map data.
mapService.ts required with getSiteMap(), getNearbyFacilities(), getRoute(), getAccessibleRoute().
Architecture should later support Google Maps, Mapbox, or OpenStreetMap.
19. Offline-First Requirements
Offline Site Packs are a CORE product capability.
Pack contains site metadata, maps, stories, audio metadata, images, facilities, accessibility information, QR content, and lightweight heritage assets.
Offline Downloads screen shows downloaded, downloading/progress, and not-downloaded states.
Actions include DOWNLOAD SITE PACK and deletion of downloaded content.
Required offlineService.ts methods: downloadSitePack(), deleteSitePack(), getDownloadedSites(), isSiteAvailableOffline(), syncOfflineData().
Show banner: “Offline Mode — Your downloaded heritage content is still available.”
App must remain usable without internet for downloaded content.
20. Multilingual Requirements
Supported language list: English, Hindi, Marathi, Bengali, Tamil, Telugu, Kannada, Gujarati, Punjabi, Malayalam.
All UI strings must come from i18n/.
Prototype must fully implement English + Hindi + Marathi.
Other languages must have architecture/placeholders.
Create en.json, hi.json, mr.json.
AI Guide should follow the language preference.
21. Accessibility Requirements
Settings: Large Text, High Contrast, Simple Language, Audio Guidance, Reduced Motion.
Site accessibility section: Accessible Entrance, Ramp, Accessible Toilet, Parking, Battery Vehicle, Rest Areas.
Availability states: ✓ Available, ⚠ Limited, ✕ Not Available.
22. Real-Time Information
Live Site Status component.
Display OPEN/CLOSED state, crowd level, weather, and closure status where data exists.
Prototype uses realistic mock data.
realtimeService.ts methods: getWeather(), getCrowdLevel(), getSiteStatus(), getClosures().
Future integrations may include Weather API, Crowd API, and Site Manager CMS.
23. Local Experiences
Categories: Artisans, Local Food, Craft Workshops, Homestays, Cultural Performances, Local Guides.
Cards: Image, Name, Location, Duration, Price, Verified badge.
Use “Verified Local Experience” where the product has verification metadata.
Do not implement real payments in this version.
Create service architecture for future booking integration.

Sections: My Plans, Saved Sites, Downloaded Sites, Audio History, Accessibility, Language, Settings.
Stats: Sites Explored, Stories Heard, Places Saved.

29. UX / Visual Product Requirements
Premium Indian heritage + modern AI visual direction.
Avoid generic AI chatbot appearance, excessive gradients, gaming UI, neon colors, overly futuristic interfaces, template-looking cards, and excessive rounded rectangles.
Visual identity: Deep Navy/Heritage Blue primary; Warm Gold/Sand secondary; Warm Ivory/Off-white background; muted green for verified/success; muted red for alerts; muted purple for AI.
Use Indian heritage photography where appropriate.
Strong typography hierarchy.
Subtle shadows.
Meaningful icons.
Reusable components instead of duplicated UI.
Overall feel: premium, trustworthy, cultural, modern, calm, professional, government/travel-tech credible.

37. Implementation Handoff Notes for Antigravity
Treat this PRD as the product-level contract; do not remove a specified capability merely because its real external integration is unavailable.
Where the source specification explicitly calls for mock/local behavior, implement a real working local/mock service rather than a dead UI placeholder.
Keep service interfaces stable so external APIs can replace mocks later.
Keep AR out of the current product surface. Only preserve architectural readiness.
Build core navigation and project structure first, then implement each feature as an independently testable working module.
Do not place business logic directly inside presentation components.
Use the specified sample heritage sites and keep their content source-oriented.
Do not invent questionable historical facts merely to fill cards or AI answers.
Verify every visible CTA, route, persistence path, offline state, and demo step before declaring the prototype complete.

39. Release Definition
The release described by this PRD is complete only when the application behaves as a real working mobile prototype across the specified screens and flows, including local persistence, search/filtering, audio controls, personalized itinerary generation, location-aware demo behavior, offline site packs, multilingual UI, accessibility settings, and API-ready service abstractions.
A static UI-only implementation does not satisfy this PRD.
40. Source Integrity Statement
This PRD is derived from the user-provided SARTHI specification. Requirements have been reorganized into product-document form for implementation clarity. No future product success, adoption, performance, factual completeness, or external API availability is predicted here. Where the source did not define a technical decision, the item is explicitly marked for TRD resolution rather than presented as a fact.
